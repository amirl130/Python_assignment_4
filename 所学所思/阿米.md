# 循环的本质

## 🤔 疑问
for循环和while循环，算同一种解法吗？

## 📝 学到的事
在求和知识库中，我分别实现了for和while累加。

两者语法不同：
- for：确定次数的循环
- while：条件控制的循环

但抽象层面做的是同一件事：**遍历所有元素，逐个累加，返回总和**。

老师说：循环不是for/while这个语法，而是「对集合元素施加同一操作并归约」的抽象模式。

## ✅ 结论
for和while在抽象层面是相同的。如果按我的判定标准（归约顺序、内存模型、调用栈结构），它们应该是同一种。

## 💡 启发
写代码时先想「抽象模式」，再选具体语法。重要的不是「怎么写」，而是「在做什么」。

# 以终为始的真意

## 🤔 疑问
「以终为始」就是「先想好再动手」吗？

## 📝 学到的事
做知识外脑时我发现，「终」不只是「最终提交物」，而是「最终使用场景」。

三个层次：
1. 提交物（老师要看什么）
2. 使用场景（我将来怎么用）
3. 思维习惯（我想成为什么样的学习者）

真正的「以终为始」是第三个层次。

## ✅ 结论
我的知识外脑应该是一个「活的」笔记系统，而不是「死的」作业存档。记录思考过程比记录知识点更有价值。

## 💡 启发
写笔记时多问「我为什么觉得这个重要」。知识外脑是给自己用的，不是给老师看的。

# 判定标准的教训

## 🤔 疑问
「什么算一种解法」这个问题，为什么这么重要？

## 📝 学到的事
没有标准时：
- 分类随意
- 数量随便数
- 别人看不懂

我的标准：**归约顺序、内存模型、调用栈结构**三者有至少一项差异，才算不同种。

但边界案例让我反思：
- `sum(lst)` vs `sum(lst,0)` → 同一种（参数默认值）
- `for` vs `while` → 应该是同一种（控制流差异不是本质）

## ✅ 结论
好的标准要可操作、可解释、可复现。标准不是一成不变的，发现错了就改。

## 💡 启发
任何分类工作，先问「我的标准是什么」。标准写在明处，让团队和老师看到。

# AI辅助学习

## 🤔 疑问
用了AI是不是显得我不行？

## 📝 学到的事
AI是工具。区别在于怎么用：

| 不好的用法 | 好的用法 |
|-----------|---------|
| 直接复制粘贴 | 读懂后重写 |
| 出错了不会修 | 能自己调试 |
| AI当答案机 | AI当讨论伙伴 |

我的原则：**读不懂的AI代码，即使能跑，也不放进知识库**。

## ✅ 结论
用AI没问题，关键是「我是否理解」。标注不是「承认作弊」，而是「展示学习过程」。

## 💡 启发
用AI的流程：生成 → 读代码 → 理解原理 → 修改完善 → 写注释 → 标注来源。

# GitHub Pages踩坑记

## 🤔 疑问
为什么我开了Pages还是看不到网页？

## 📝 学到的坑

| 问题 | 解决 |
|------|------|
| Pages打不开 | Settings → Pages → Branch选main |
| 找不到Change theme | 创建 `_config.yml` 写 `theme: jekyll-theme-cayman` |
| 文件夹里的文件看不到 | 在README.md写链接，或放 `index.md` |
| 修改后不更新 | 等1-2分钟，强制刷新 |

## ✅ 结论
GitHub Pages不难，但需要耐心。先让东西「能用」，再追求「好看」。

## 💡 启发
遇到问题先查官方文档。把配置过程记下来，下次直接用。
